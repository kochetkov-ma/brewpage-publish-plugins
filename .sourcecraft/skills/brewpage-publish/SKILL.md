# Публикация на BrewPage

Опубликуй `{{ path }}` из этого репозитория на [BrewPage](https://brewpage.app). Введённые поля относятся к одной публикации выбранного файла или собранного сайта. Локальный черновик подготовь и верни без обращения к BrewPage. Следуй общим инструкциям [публикации](upstream/references/publishing.md) и [владения](upstream/references/ownership.md).

## Перед отправкой

1. Разреши `{{ path }}` в существующий абсолютный путь внутри репозитория. Выбери готовый файл или каталог сборки с HTML. Проверь, что содержимое не включает секреты, личные данные и исходники проекта.
2. Соблюдай `{{ visibility }}`. Значение `public` допускает размещение в галерее и индексацию, если формат поддерживает их. `private` открывает публикацию по ссылке без индексации. Другая величина поля требует выбора пользователя.
3. Передай явно заданный `{{ ttl }}` как целое число от 1. Срок из квитанции имеет приоритет над запрошенным. Для крупного сайта проверь ограничения способом, доступным на выбранном маршруте.

## Выбор способа до первой записи

1. Определи выбранного владельца по [рецепту владения](upstream/references/ownership.md). Если другой владелец не выбран, предпочти подходящий уже подключённый аккаунт. Проверь фактически доступный в этой сессии инструмент BrewPage MCP, его схему, поддержку выбранного материала и настроек, полномочия владельца и приватность результата. При необходимости один раз воспользуйся предусмотренным средой обнаружением инструментов. Установка пакета или доступность URL не подтверждают доступ к инструменту.
2. Для публикации в выбранном аккаунте используй подходящее подключение MCP и `requireAccount: true` при явном запросе на аккаунт. Если подходящее подключение отсутствует, оставь публикацию ожидающей и назови недостающий шаг подключения. Явный запрос «только MCP» также остаётся ожидающим, если инструмент не подходит. Для явно выбранного нового анонимного владельца используй путь без OAuth-токена и сохранённого ключа.
3. Используй совместимый MCP, когда он доступен и приватность выдачи любого ключа или ссылки управления проверена. Для нового анонимного ключа заранее согласуй защищённое сохранение или передачу только владельцу. Если совместимого MCP нет, выбери защищённый REST только до первой записи и только если запрос, права среды и доказательство того же владельца разрешают этот путь. Если подходящего пути нет, верни готовый материал и конкретный недостающий шаг.

## Публикация через MCP

Проверь локальный материал по [рецепту проверки для MCP](upstream/references/publishing.md#check-inputs-for-mcp) до передачи содержимого. Передавай только проверенные исходные байты или текст, полный набор файлов сайта с относительными путями и выбранную точку входа. Для исходного HTML нужна поддержка точного сохранения. Локальный путь нельзя использовать как URL для импорта. Если схема не может принять материал целиком, вернись к выбору способа до записи.

Используй фактически доступную схему. Для компактного `publish` передай `namespace: "public"` при выборе `public` и опусти `namespace` при выборе `private`, если это даёт запрошенный доступ для выбранного владельца. Передай явно запрошенный срок как `ttlDays`, пустое значение оставь без параметра. Сделай один вызов и верни точную ссылку для чтения, фактический доступ, срок и важные уведомления из результата. Обработай выданные приватные данные по [рецепту владения](upstream/references/ownership.md). Подключённый аккаунт сам хранит своё подтверждение доступа.

## Публикация через REST

Для этого пути проверь разрешённое постоянное хранилище владельца для рабочей области. Используй отдельный абсолютный каталог SourceCraft вне репозитория и выбранных материалов. Он должен принадлежать владельцу процесса, иметь режим `0700` и не быть символьной ссылкой. Исполнитель сохраняет в нём `.claude/brewpage-history.md` и при необходимости `.claude/brewpage-recovery.json` как файлы `0600`. Используй одно и то же хранилище при следующих вызовах. Если хранилище недоступно, оставь отправку через REST ожидающей.

Подставь абсолютный путь к поставляемому `upstream/scripts/brewpage-run.sh` вместо `{runner}`. Используй среду с рабочим `PATH`, проверенным каталогом состояния в `CLAUDE_PROJECT_DIR` и без переменных конфигурации Git, других клиентов и их сессий. Исполнитель отправляет `User-Agent: brewpage-sourcecraft/1.1.4 (+https://brewpage.app)`.

Для `public` передай `--ns public`, для `private` передай `--ns my`. Пустой срок оставь как `--ttl ''`. Исполнитель запросит 15 дней. Для нового анонимного владельца используй `--anonymous`. Для отдельно выбранного владельца используй его защищённое доказательство по рецепту владения.

Каждую строку выполняй отдельной командой. Подставляй значения как аргументы в одинарных кавычках, а внутреннюю `'` записывай как `'\''`. Для файла используй `{kind}` = `file` и для сборки `{kind}` = `site-dir`. Исполнитель сам публикует HTML и Markdown как страницы и выбирает входной файл сайта. Укажи `--entry` только для явно выбранной точки входа.

```bash
bash '{runner}' probe '{path}'
bash '{runner}' preflight {kind} --path '{path}'
```

Покажи тип, размер, доступ, запрошенный срок и для сайта перечень проверенных файлов и точку входа. При `CONFIRM` действуй по инструкции публикации: покажи отмеченные допустимые файлы и получи согласие на точный `REVIEW_SHA256`. Передай те же `--confirmed --review-sha256 '{digest}'` при подготовке и отправке. Если содержимое изменилось, согласуй новый список. При `FAILED` остановись. Освободи временную копию по выданному `RUN:` командой `cleanup --run '{run_id}'` после проверки или отмены.

```bash
bash '{runner}' publish {kind} --ns '{ns}' --ttl '{days}' --password-file '' --path '{path}'
```

Исполнитель заново проверит файлы перед отправкой и использует сохранённый ключ, если владелец уже выбран. Неразрешённый выбор владельца оставляет публикацию ожидающей. Если SourceCraft не предоставляет нужный исполнитель, доступ к сети или защищённое хранилище, верни путь к готовому материалу и назови недостающий шаг.

## Квитанция REST

Верни точную ссылку из `OK`, фактические условия доступа и важные `NOTICE` / `VISIBILITY`. Укажи срок окончания из `expiresAt`, если он доступен в полученной квитанции. Сообщи о сохранении ключа только после `OWNER TOKEN SAVED`. Исполнитель никогда не печатает ключ владельца и ссылку управления, даже с `--private-output`: этот флаг лишь называет защищённое хранилище, и его добавляют только в проверенном канале, где и вывод инструмента, и ответ доступны только владельцу. Ключ и ссылка управления остаются в защищённой истории; сообщи владельцу её расположение только в таком канале. Любой, кто получил ссылку управления, может управлять публикацией. Если владелец отказался от истории, заранее согласуй существующую папку только для владельца (права `0700`, вне рабочей папки и любого Git-репозитория) и передай `--no-save --receipt-dir '/абсолютный/путь'`: файл `brewpage-recovery.json` (права `0600`) сохранит ключ и ссылку.

Если публикация подтверждена, а сохранение ключа не удалось, следуй [восстановлению](upstream/references/ownership.md): команда `owner-recovery --private-output` в защищённом канале сообщает только адрес владельца и ссылку для чтения; затем передай путь к квитанции в `owner-store` через `--owner-token-file` с этими точными адресами. Без такого канала оставь квитанцию в хранилище и сообщи о незавершённом восстановлении без ключей и приватных ссылок.

## Отказ или неопределённый результат

На любом маршруте при отказе сообщи безопасную причину и остановись. При тайм-ауте или неопределённом результате оставь запрос на сверке через выбранного владельца и его квитанцию. Не отправляй повторный запрос и не переходи на другой способ публикации.
